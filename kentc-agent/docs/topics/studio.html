10 · Studio 應用框架

一個三頁非同步迴圈；換一份 YAML，就是新的應用

問題

上傳文件不可信：代理直接產生報告頁，注入文字可進入畫面。每個情境各寫一份前端 ≈ 750 行 JS。

核心想法

共用三頁非同步迴圈，差異只寫在 app.yaml。代理只回傳通過 schema 與 checks 的 JSON，前端以固定區塊呈現；設定錯誤啟動即拒。

依據

同一套程式跑 TER 審查與 RM 洞察兩個應用。本機實測：標記錯誤值只重跑該檔；失敗明確顯示，重試成功（見 ③）。

問題：網頁應用面對不可信輸入與不斷增加的情境

  • 輸入不可信：上傳文件可夾帶指令；代理有 bash 或網路 → 實際動作或資料外流。
  • 輸出須可核對：分析師逐筆核對事實與位置、標記錯誤、要求重跑；長文無法拆解。
  • 情境持續增加：TER 審查、RM 財富洞察……欄位、文件、報告各異；每情境複製前端 → 維護成本線性成長。
  • 本機模型一次一個工作：使用者不能在畫面前等每個代理。

核心想法：一個迴圈、一份 YAML、固定的區塊

config/apps/<name>/app.yaml 即工作流程：每個代理（通道 agent:、report:、extras.<name>:）＝契約＋技能（kentc-agent/skills/，各應用共用）；程式與前端只有一份。

第 1 頁 輸入與追蹤 應用欄位 ＋ 檔案通道 ＋ 資料擷取 ──► 洞察代理（逐檔／逐通道）、SQL 擷取（不用模型、平行） ▲ │ 非同步：案件表即時更新狀態 │ 每次非同步動作後回到案件表 ▼ 第 2 頁 核對洞察 標記錯誤值／對檔案或通道留備註 ──► 只重跑該代理；隨時補檔 │ │ 產生報告（等待尚未完成的工作） ▼ ▼ 第 3 頁 報告與提示 報告框架 ＋ 應用的 view ＋ 建議的下一步；一則提示 ──► 一個新版本（案件表顯示 NEW vN）
  1. ① 第 1 頁 → 第 2 頁每通道一個洞察代理；per 定工作單位：file（預設）每檔一個，lane 整通道一次。
  2. ② 第 2 頁 → 第 2 頁標記事實或留備註 → 只重跑該檔（或通道）的代理，附前次結果與備註。
  3. ③ 第 2 頁 → 第 3 頁報告代理讀全部材料（見代理契約表），先等未完成工作。
  4. ④ 第 3 頁 → 第 3 頁一則提示＝一個報告工作：前一版＋提示 → 新版本，以 reply 回答。
# config/apps/ter/app.yaml（節錄）
title: TER review
case: {label: TER case ID}  # 編號前綴預設為 TER-<年>-；標籤預設由名稱產生
fields:                     # 第 1 頁表單；column: 顯示在案件表
  - {name: cif, label: Customer CIF, required: true, column: true}
  - {name: trigger, label: Trigger event, type: textarea, required: true}
lanes:                      # 檔案通道 → 讀它的代理 → 第 2 頁如何呈現
  - name: context
    required: true
    agent:
      label: Context agent
      per: lane                          # 整個通道一次
      skills: [ter-trigger-context]      # kentc-agent/skills/<name>.md
      output: {trigger_type: string, trigger_event: string}
    view: [{title: Trigger context, kv: [trigger_type, trigger_event]}]
  - name: evidence
    agent:                               # 不寫 view：依 output 形狀呈現
      label: Doc agent
      per: file                          # 每檔一個工作（預設）
      skills: [ter-evidence, document-extraction]
      tools: [read]                      # 預設 [read]；[] 表示無工具；永不 bash
      max_turns: 100                     # 整個工作（含修正）的模型呼叫數；0 = 不限
      output: {document_type: string, key_values: [{field: string, value: string, location: string, confidence: number}]}
      checks:                            # required、A..B、min N / max N、match REGEX
        key_values[].location: required
        key_values[].confidence: 0..100
pulls: [kyc_profile, txn_history]
report:                     # 第 3 頁
  name: TER report
  skills: [ter-report, fincrime-guardrails]
  output: {...}             # 報告框架欄位 ＋ 應用自己的欄位（節錄略）
  verdicts: {Agree: ok, Further investigation: warn}
  hide: [confidence]        # 不呈現的 output 欄位
  view:                     # 只寫需要自訂的區塊；其餘欄位依預設接在後面
    - {title: Executive narrative, text: executive_narrative}
    - {title: Key risks, cards: key_risks, head: title, score: score}

output 管內容，view 管呈現

代理依 output 回傳 JSON，須過 checks；前端與 Markdown 匯出只用固定區塊類型。代理從不產生 HTML，前端一律跳脫。

view 可省略，只寫自訂區塊（順序、標籤、計分卡片）；其餘頂層欄位依 output 順序與形狀：物件 → kv、事實清單 → facts、其他物件清單 → table、字串清單 → list、連續單值 → 一個 kv。hide：不呈現的欄位。路徑、選項、hide 啟動時皆對照 output，打錯即拒並指出位置。

case_brief 由欄位自動產生：案件、應用、依欄位順序的已填「標籤: 值」；無模板 → 不與欄位脫節。

小模型只填領域欄位（如 score: number），驗證仍嚴格；新情境多半只需欄位、通道、代理契約、技能。

技能與契約

技能（skills）負責方法、app.yaml 負責契約

技能＝kentc-agent/skills/<name>.md（與 config/ 並列；studio.yaml 以 skills: ../skills 指定）。前置資料 description: 可選，只給人看；本文原樣（非 Jinja）放入系統提示，標題 ## Skill: <name>，角色技能居首。找什麼、如何判斷與撰寫 → 技能；YAML 無提示文字，只有 per、skills、tools、max_turns、output、checks。

內建技能：document-extraction、report-revision、fincrime-guardrails、ter-trigger-context、ter-evidence、ter-investigation、ter-report、rm-sources、rm-report。

執行

做到通過 checks，或用完 max_turns

Studio 在記憶體組出單步驟執行，交給同一引擎（kentc_agent.workflow.Runner）。任務訊息＝角色輸入（空者省略；lane_file、materials_file、previous_report_file 內嵌為文字；file 由代理 read）＋ output 形狀 ＋ checks。不合格 → 附確切錯誤退回；max_turns 計整個工作（含修正）。

CLI 工作流程步驟仍為 2 次修正；Studio 代理不能從 CLI 以路徑執行（config/cli/workflows/ 不變）。

固定的區塊類型（前端 renderBlocks 與 Markdown 匯出共用）
區塊路徑指向選項
text字串（或字串清單：分段）—
kv物件，或一組路徑labels
table物件清單columns（鍵 → 欄名，或鍵清單）
list字串清單—
chips字串或物件清單（首值粗體）—
cards物件清單head、kicker、score（0–100 環形，並排序）、body、notes
facts{field, value, location, confidence} 清單僅第 2 頁：分析師逐列標記
報告框架

每個報告代理都必須回傳五個欄位

title；verdict（output 中 "A|B" 之一；verdicts 指定色調 ok／warn／bad／info，顯示於案件表）；reply（回答本次提示）；requests（[{document, reason}]）；questions（未解問題）。其餘欄位屬應用，由 report.view 呈現。

requests、questions 置於報告末「建議的下一步」（接在應用自身建議後，如 TER 的 Recommended next step）：待索取文件附上傳按鈕 → 回第 2 頁核對後重新產生；未解問題一鍵帶入提示。

缺欄位，或 verdicts 與 output 選項不一致 → 啟動即拒。

非同步提示

一則提示＝一個新版本；不是即時對話

第 3 頁只呈現報告；右側可收合面板只收提示。送出即回案件表：該列「Revising … → vN」，完成後 NEW vN 與「Open vN →」。新版本開頭列出本次提示與 reply；舊版本見版本選單。

第 2 頁「產生報告」、第 3 頁「重新產生」同為非同步。提示＝報告工作的 instruction，隨版本記錄，case.json 不另存對話；版本與決策軌跡（HUM／AGT／SYS）一一對應。

代理契約：Studio 依角色固定傳入，代理不必宣告
代理輸入材料
通道代理 · per: filefile（docs/<name>）、case_brief、feedback、previous每檔一工作；代理自行 read；有備註附前次結果
通道代理 · per: lanelane_file、case_brief、feedback整通道一工作；檔案（含附件）先轉文字，內嵌任務訊息
報告代理materials_file、case_brief、instruction、previous_report_filematerials.json：案件欄位、逐檔洞察、lane_insights、資料擷取關鍵值與 CSV 路徑、額外代理、分析師修正
額外代理materials_file、case_brief同上；分析師逐次勾選
設定錯誤啟動即拒，不留到畫面。 另檢查：技能存在且非空；有 output；工具皆已知且無 bash；check 路徑在 output 中且合規（範圍限數字、min／max 限清單或字串、match 限字串）；資料擷取 SQL 只綁定該應用欄位（及 :case_id）。外部（url:）代理不接受 skills／output／checks，須寫 view；形狀執行時才知，缺路徑顯示空白。
設計取捨：代理的成果如何變成畫面
方案小模型負擔驗證與安全新增使用情境的成本結論
A · 代理直接產生 HTML 報告高：版面＋內容上傳文件的注入文字可入頁；結構無法驗證低不採用：違反「輸入與輸出由系統定義」
B · 代理直接輸出通用區塊高：在抽象版面中填內容schema 無法表達「多種區塊之一」；失去領域型別（如 score: number）低不採用
C · 每個使用情境複製一份前端低可行，各自維護高：≈ 750 行 JS／情境不採用：即原 TER 專用狀態
D · 領域 output ＋ 應用 view ＋ 固定區塊低：只填領域欄位output＋checks 嚴格驗證；view 啟動時對照；前端一律跳脫低：一資料夾＋一行設定採用
應用 · ter

TER review

通道：Context（必填）→ context 代理（逐通道，Trigger Context）；Evidence → doc 代理（逐檔，關鍵值與異常）；五項核心銀行資料擷取；額外代理：investigation。

報告：評估、執行摘要、觸發事件、背景、KYC、交易審查、計分的關鍵風險、建議下一步；verdict：Agree／Further investigation。

應用 · rm

RM insight

通道：Sources（必填）→ source 代理（逐檔：來源系統、事實、陳述／推論關係、訊號）；無資料擷取。估算一律附算式（無 bash）。

報告：AURA 四大支柱（排序的目標客戶、關係證據、逐一回答、證據鏈）、RM 協作、來源出處；verdict：Proceed／Controlled review／Insufficient evidence。
