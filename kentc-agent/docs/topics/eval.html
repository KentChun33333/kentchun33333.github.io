07 · 長任務的上下文：摘要 → 主題筆記

摘要會遺失細節：從單一摘要壓縮到主題筆記

問題

舊版（v1，已移除）把舊歷史壓成單一摘要。長任務的精確細節（帳號、金額、版本、關聯）在壓縮中遺失 → 代理被迫重找證據。

核心想法

壓縮時分流：短 checkpoint 記進度，細節寫入可回讀的本地主題筆記，寫入並驗證後才丟棄舊歷史。無新工具、無配額、無背景程序。

依據

歷史 A/B（v1 已移除）4 次重複、同模型同任務：STR 中位數 v1 0.65、v2 0.60，不分勝負；v2 交檔較穩（HTML 3/4 對 1/4），v1 較守格式（B 1.00 對 0.68）。記憶回復實質皆 8/8，v2 呼叫與 tokens 在 failed_repair 減半（見 ④）。

問題：單一摘要在長任務中遺失細節的三個位置

舊版 v1（單一摘要壓縮，統一後已移除）的縱向壓縮與橫向外存（見 04 · 上下文視窗）夠用於短任務。長任務（如審查案：數十位客戶、上百筆交易）的細節須撐過多次壓縮，v1 在三處流失：

  • 單一摘要：細節與進度爭篇幅 → 越壓越粗。
  • 摘要模型視野受限：每筆舊工具結果只送前 2,000 字 → 後段證據（帳號、修訂版本）進不了摘要。
  • 失敗即截短：壓縮失敗時截短舊工具結果 → 細節消失。

遺失後只能重讀原始檔；呼叫次數有限時，重讀擠掉寫報告的次數。

先嘗試過的方案：分層記憶（已移除）

第一版 v2：熱／冷兩層、SQLite、背景整理（curator）、檢索帳本與配額、專用 context_search／context_read。小模型上反而引入新失敗：

教訓：每多一個工具、配額或背景機制，小模型就多一種失敗，且常在記憶派上用場前 → 目前的 runtime 做減法。紀錄見 str-benchmark.md、memory-comparison.md。

核心想法：checkpoint ＋ 主題筆記，只用一般工具回想

目前唯一 runtime＝src/kentc_agent/（即原 v2，主題筆記壓縮）。v1（單一摘要）已移除，下方 v1 欄與 ④ 的數據僅為歷史對照。細節見 session-memory-design.md。

兩組測試任務：為什麼這樣設計

短任務 · compare_memory.py

記憶回復：壓縮後能否找回細節

預匯入 32 批、66 則讀檔紀錄（≈ 65k tokens > 62,536 − reserve）→ 首次請求即壓縮。關鍵證據放在每筆結果前 2,000 字之外（摘要模型看不到）。

buried_revision：在舊核准版、核准版＋簽署修訂、未核准提案間，找出生效版本、配額、區域與完整 rollback SHA。failed_repair：須實跑 verify.py --strict，區分兩次相同 decoder 錯誤、同代碼異路徑的 cache 錯誤、一則未驗證的「已修好」。

限制：8 次呼叫、僅 read／bash、只評 JSON 欄位、無部分分數。兩版皆可重讀 evidence.log → 測找回證據，非純記憶。

長任務 · str_benchmark.py

STR 審查：從空 session 做完一件真實規模的工作

40 位客戶、121 檔、≈ 242,000 字元（≈ 6 萬 tokens，讀一遍近滿視窗）：KYC、RM 筆記、公司登記、信託契據、交易明細、媒體報導 → 必然壓縮。洗錢網路藏在縮寫名稱、帳號、共用聯絡資料後；干擾項（同名者、無關報導、正當信託、有合理說明的現金存款）測精準度。

交付 report/findings.json、report/index.html，確定性評分：A 整體判斷 0.25、B 交叉辨識 0.45、C 報告 0.30。

限制：80 次呼叫、單次回覆 ≤ 4,096 tokens；未交檔 → C = 0。詳見 str-benchmark.md。
