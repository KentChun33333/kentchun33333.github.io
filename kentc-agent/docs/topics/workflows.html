09 · Finite-State Workflow 確定性狀態機（src/kentc_agent/fsm_workflow.py）

同一隻 Agent 加上前後護欄：從 Main Agent 到 State-Machine Agent

問題

線性步驟無法回跳修正；共用長對話會造成 REVIEW 球員兼裁判與上下文膨脹；小型本機模型常出現 false DONE（自稱測試通過但真實 exit code 非 0）。

核心想法

以 Finite-State Workflow（fsm_workflow.py） 統一工作流程引擎：100% 純 fresh（每個 state 是套上 Precondition / Postcondition 的同一隻 kentc_agent.Agent，靠磁碟 Artifact 交接）、獨立 Runtime Validator 取真實證據、零模型呼叫 exit_gate 把關 DONE。

依據

實作於 src/kentc_agent/fsm_workflow.py，涵蓋 7 份內建 YAML（含 coding-loop.yaml），整合進 Breezeman 排程與頂部 Workflows 設定專區，由 tests/test_fsm_workflow.py 完整驗證。

四種 State 類型與客觀 Validator 清單

四種 State 類型

  • prompt: — 新鮮 Agent 執行任務，可搭 skills:、tools:、format: json、schema:、checks:、output:。
  • gate: true — 零模型呼叫的確定性閘門，僅跑 validators: 決定 passed / failed。
  • ask: — 人工審核門（非互動時拋 NeedsAnswer，以 --resume --answer 或 Breezeman UI 續跑），依回答直接路由。
  • web: — 隔離網路研究子代理（支援 plan、foreach 與 approve: true），簡報落盤交付。

獨立 Runtime Validators

  • command: — 由 runtime 在工作區直接執行命令，exit_code == 0 才算通過。
  • file_exists: — 驗證目標產出檔確實存在於工作區且非空。
  • git_diff: true — 驗證工作區確實有實際變更。
  • expr: — 針對 step_data、data、steps 與 evidence 的確定性布林檢查。

實戰撰寫指南：如何寫一份 Finite-State Workflow YAML

把 YAML 放進工作區的 workflows/<name>.yaml（或在 Breezeman 頂部 Workflows → + New Workflow 編輯並按 Validate & Save），引擎載入時會自動檢查所有路由、工具與 exit_gate 不變量：

# workflows/my-feature-loop.yaml（完整最小範本）
name: my-feature-loop
version: 2
description: Plan -> Implement -> Test -> Exit Gate

runtime:
  max_cycles: 12             # 總狀態執行次數上限 → PAUSE
  max_retries_per_state: 3   # 單狀態連敗上限 → ESCALATE
  no_progress_limit: 2       # 連續相同失敗簽章 → PAUSE
  max_total_tokens: 300000   # 選填 token 上限（0 = 不限）
  max_step_seconds: 300      # 驗證命令逾時秒數

instructions: |
  Objective: {{ prompt }}
  Keep edits minimal and cite exact file paths.

tools: [read, write, edit, bash]  # 預設工具白名單
max_turns: 20                     # 每 state 模型呼叫上限
entry: plan                       # 狀態機起點

states:
  plan:
    tools: [read, bash]           # 覆寫為唯讀＋查檔
    skills: [document-extraction] # 懶載入 skills/<name>.md
    prompt: "Plan the work for: {{ prompt }}"
    format: json
    schema:
      task: string
      files: [string]
    routes:
      default: implement

  implement:
    prompt: |
      Task: {{ prompt }}
      Plan: {{ steps.plan.data | json }}
      {% if steps.test is defined and steps.test.evidence %}
      Previous test failure: {{ steps.test.evidence | json }}
      {% endif %}
    validators:
      - name: has_changes
        git_diff: true
    routes:
      passed: test
      failed: implement

  test:
    tools: [read, bash]
    prompt: "Verify the implementation."
    validators:
      - name: unit_tests
        command: "uv run pytest -q"  # Runtime 直接執行取 exit_code
    routes:
      passed: exit_gate
      failed: implement

  exit_gate:
    gate: true                    # 零 LLM 呼叫的確定性閘門
    validators:
      - name: final_tests
        command: "uv run pytest -q"
    routes:
      passed: DONE
      failed: implement

模板變數與內建工具速查

因為每個 state 都是 100% 純 fresh，跨狀態交接一律靠以下模板變數：

  • {{ prompt }}：呼叫端傳入的任務目標（CLI 位置參數或 Breezeman Schedule Prompt 框），不需宣告 inputs:。
  • {{ steps.<id>.output }}：前面某 state 的文字回覆。
  • {{ steps.<id>.data | json }}：前面某 JSON state 通過 schema 驗證的結構化資料。
  • {{ steps.<id>.evidence | json }}：前面 state 的客觀 validator 輸出（含真實 exit_code、stderr）。
  • {{ data.<key> }}：所有前面 JSON state 合併後的快捷鍵。
  • {{ workspace }}、{{ run_dir }}、{{ cycles }}：目前工作區路徑、執行目錄與週期數。
  • 內建函式：documents('.')、glob('*.pdf')、read_file('notes/a.md')；filter：| json、| fromjson、| slug。

撰寫避坑檢查表

  • 不可繞過 exit_gate：只要有任一 gate: true 狀態，任何 prompt 狀態的 routes 都不得直接指到 DONE（載入即拒）。
  • 避開 YAML 1.1 布林鍵：routes: 不要寫未加引號的 yes: / no:（會被解析成布林），請寫 approve: / reject: 或加引號。
  • expr: 用 Jinja2 語法：請寫 steps.work.output != '' 或 step_data.verdict == 'approved'（不要用 Python 內建 bool()）。
  • 自訂條件路由：若要依 JSON 欄位值分支，加 route_on: "step_data.action" 並在 routes: 列出白名單鍵值（未知值預設 fail-closed → ESCALATE）。
YAML 欄位完整速查表（fsm_workflow.py）
層級欄位說明
頂層name、description、entry、states工作流名稱、說明、起點 state id（預設第一個 state）與所有狀態定義。
頂層（選配）instructions、tools、max_turns、effort、skills_dir、inputs全狀態共用系統指令與預設上限；inputs: 僅在確實需要額外結構化參數（如 test_cmd 預設值）時選用。
runtime:max_cycles、max_retries_per_state、no_progress_limit、max_total_tokens、max_step_seconds、fail_closed_on_unknown_event確定性資源與迴圈護欄；超限自動進入 PAUSE 或 ESCALATE。
states.<id>四選一：prompt｜gate: true｜ask｜web決定該 state 類型；prompt 可搭 tools、skills、format: json、schema、checks、output、validators、route_on、routes。
終止態DONE、PAUSE、ESCALATE保留字，不可作為 state id；由 routes 或 runtime 護欄進入。

零呼叫端假設（原生 {{ prompt }}）：Finite-State Workflow YAML 不假設呼叫端是 CLI、Breezeman 排程或 Studio。引擎原生內建 {{ prompt }} 與 {{ workspace }}，通用流程（如 coding-loop、case-review、docs-first-insight）不需宣告多餘的 inputs:；CLI 可直接執行 kentc-agent --workflow coding-loop "目標描述"，Breezeman 則由頂部列 Workflows 專區管理 YAML，並在任務右側 Schedule → Finite-State Workflow 以單一 Task Prompt 定時或立即觸發（詳見 B1 · 排程狀態機與長程韌性）。
