08 · 單任務長程記憶的抗膨脹演算法

LSM 分層封存：活頭有界，冷檔不可變

問題

長任務跨天／跨週執行後，單一主題筆記與 SIM 失敗帳本會持續膨脹，最終超過 compaction_max_output_tokens 或視窗上限，導致壓縮永久失敗或讀取失控。

核心想法

借鏡資料庫 LSM-Tree（Log-Structured Merge-Tree）：寫入永遠落在有界熱段（L0），超過門檻即 Seal（封存為不可變冷分片 L2）＋ Roll（滾動蒸餾輕量活頭），零靜默刪改。

依據

由 compaction.py（topic_seal_threshold）、dream.py（seal_and_roll_sim）實作，並由 test_topic_compaction.py 與 test_breezeman_dream.py 回歸驗證。

問題：為什麼需要 MERGE？又為什麼不能只靠 MERGE？

先分清楚兩個動作各自解決什麼問題：

  • 為什麼需要 MERGE（筆記還小時）：如果不做原地合併、每次壓縮都只往筆記後面純追加，api.md 很快會堆滿重複敘述與互相打架的舊值（例如 port=8000 後面又寫 port=9000）。主代理之後 read 會浪費大量 token 甚至抓錯舊值。MERGE 的價值是優化讀取品質——在筆記還小時，把舊筆記＋新更新整理成一份去重、乾淨、標明取代關係的現行版。
  • 為什麼不能只靠 MERGE（筆記長大後）：MERGE 要求模型在單次回覆吐出整份替換後的完整 Markdown。一旦長任務跨天／跨週累積大量無法刪除的獨立事實，筆記逼近輸出預算 compaction_max_output_tokens（例如 8,192 tokens），合併就會被 finish == "length" 截斷而報 CompactionError。

白話看懂 L0 / L1 / L2（白板、目錄、檔案櫃）

L0 · 熱層（活頭）

桌上的白板

模型平常直接讀寫的活躍筆記（例如 api.md 或 SIM 活頭）。永遠維持輕量有界，確保每次 read 都快、準、不爆視窗。

L1 · 溫層（索引）

目錄頁（O(1) 路由）

_index.md 與 memory/INDEX.md。只列標題與路徑指標，讓代理一眼知道「最新狀態在活頭、上週細節在 era-001」。

L2 · 冷層（封存）

上鎖的檔案櫃

不可變的歷史快照（api-era-001.md、archive/sim/*-log.md）。零靜默刪除、永不再改寫，只有需要核對細節時才用 read/rg 去翻。

1. Topic Note Seal & Roll

      
觸發門檻由輸出預算與視窗共同決定：

      
T_topic = max(256, min(floor(0.65 * max_output_tokens), W // 8))

      
當 existing_tokens + update_tokens > T_topic 時：

      
    
        
  • Seal：原封不動把舊筆記寫成 <slug>-era-001.md（自動進入 Session 世代與 SHA-256 校驗）。
    • 
        
  • Roll：以 ROLL_TOPIC 蒸餾出精簡活頭並置頂冷檔指標；後續 EXTRACT 自動過濾 *-era-NNN，確保冷分片永不被改寫。
    • 
        
  • 安全底線：若單份舊筆記本身已大到連 ROLL_TOPIC 都放不進視窗，仍原子失敗並拋出 CompactionError，絕不靜默截斷。
    • 
      

    

    

      
2. SIM 帳本 Seal & Roll

      
觸發條件（任一成立且條目數 > 3）：

      
approx_tokens(body) > 2,000  OR  entries > 8

      
執行步驟（seal_and_roll_sim）：

      
    
        
  • Seal：將最舊的 N - 3 條 ### [YYYY-MM-DD] 紀錄追加寫入 memory/archive/sim/<slug>-log.md。
    • 
        
  • Distill Head：以 SIM_ROLL_PROMPT 整理為 ## Active Strategy ＋ ## Known Pitfalls (Do Not Repeat)，接上最近 3 筆原文與冷檔路徑。
    • 
        
  • 審計保留：舊嘗試與舊世代快照均保留於磁碟，不作破壞性刪除。
    •
