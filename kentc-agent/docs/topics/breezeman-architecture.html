B0 · Breezeman 宿主總覽與 FastAPI 執行層

單一宿主承載長程對話、排程、記憶與 Studio

問題

kentc_agent 是同步單任務迴圈，無法直接承載常駐網頁 UI、即時串流、多任務子工作區、定時排程、跨會話記憶蒸餾與結構化案件介面。

核心想法

以單一 FastAPI 宿主（app.py）統一對外：雙獨立背景協程驅動排程與 Dreaming；每個 Task 綁定一隻 Chat（同一個 Agent + Session），透過 daemon=True worker 執行緒非同步跑動；Studio 以資料夾內嵌掛載於 /studios/{id}/。

依據

實作於 src/kentc_breezeman/app.py、runtime.py、server.py、studio.py 與 workspace.py，由 test_breezeman.py 與 test_breezeman_studio.py 驗證。

問題：為什麼需要 Breezeman 宿主層（而非另造多代理框架）

  • 同步核心 vs. 非同步服務：kentc_agent.Agent.run() 為同步阻塞呼叫（含檔案讀取、bash 與多輪模型往返）；若直接放進 FastAPI event loop 會凍結整個伺服器。
  • 人機與排程共享同一脈絡：長程任務需要定時自主推進，但使用者隨時可能打開介面查看進度、按 Stop 中止、或直接插話接手——若排程另開隔離子代理，人機上下文就會割裂。
  • 過去獨立 Studio 的割裂問題：過去若把 Studio 當成獨立伺服器啟動，會與日常 Task 工作區、檔案樹及全域記憶（memory/INDEX.md）脫節；現在統一由 Breezeman 內嵌掛載。

併發模型設計：單一 Chat ＋ Daemon Worker（零多餘抽象）

互斥與串流

為什麼排程不開 Subagent，而是用同一個 Chat？

每個 Task 在 tasks.json 對應唯一 chat_key 與專屬子資料夾（tasks/<slug>/）。無論是使用者從 WebSocket 送訊息，還是排程器透過 tick_schedules() 觸發，都呼叫同一隻 Chat.send()，在 self._lock 下檢查 self.busy 後啟動 daemon=True 執行緒。

好處：排程與人機互動共享同一份對話歷史、checkpoint、主題筆記與即時 WebSocket 事件流，零狀態同步成本。

鎖隔離

四把細粒度鎖，避免互相阻塞

  • Chat._lock：保護單一對話的 busy 狀態與事件環形緩衝區（最多 4,000 筆，連續 delta 自動合併）。
  • Runtime._lock：保護已開啟的 _chats 字典快取。
  • Runtime._tasks_lock：保護 tasks.json 的原子讀寫（.tmp → replace）。
  • Runtime._dream_lock：非阻塞獲取，確保同時只跑一輪 Dreaming 且不卡住任何 Task 排程。
