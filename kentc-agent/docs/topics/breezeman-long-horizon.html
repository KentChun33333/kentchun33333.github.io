B1 · Breezeman 排程核心與長程韌性

非同步 Worker 結算、指數退避與防壓縮震盪

問題

排程在背景跑數週會遇到五種真實失效：只看同步派發漏接 worker 內的 LLM／超限失敗；失敗重試把相同 user prompt 疊滿 session；大系統提示觸發每次強制壓縮震盪；跨午夜日期過期；進程重啟留下殭屍 running 狀態。

核心想法

將派發（running）與結算（on_complete + settled_run_id）分離，讓 worker 故障真正觸發指數退避與熔斷；預壓縮改算動態剩餘視窗；重試去重尾端未回覆提示；重啟自動標記 interrupted。

依據

實作於 runtime.py、app.py 與 agent/loop.py，由 test_breezeman_dream.py 新增的 5 組長程回歸測試完整覆蓋。

問題：為什麼「失敗了下一輪重跑一樣」在長程代理不成立

  • Fire-and-forget 斷層：Chat.send() 啟動背景 daemon thread 就立刻返回。若排程器在派發當下就把 consecutive_errors 歸零，則 worker 裡發生的 LLMError、ContextOverflow、CompactionError 或 429 限流完全不會觸發熔斷，儀表板還會顯示假綠燈。
  • 失敗會污染 Session 狀態：Agent.run() 會在呼叫模型前把 user 訊息寫進 session。若未做尾端去重，連續失敗 10 次就會在上下文堆出 10 份一模一樣的未回覆指令，讓 ContextOverflow 越重試越嚴重。
  • 固定提示引發預壓縮震盪：若 pre_compact_ratio = 0.5 直接拿總 context_tokens() 跟 window * 0.5 比，只要系統提示（AGENTS.md + persona + skill + tools）本身佔掉一半視窗，每一次排程觸發都會強制壓縮上一輪對話。
  • 長駐執行體的時間與重啟漂移：常駐多天的 Chat 實例若在建構時寫死 Date: YYYY-MM-DD，跨天後日期就過期；伺服器重啟時，中斷在半路的排程若不清理會永遠卡在 running。

核心想法一：非同步派發與無競態結算（run_id 護欄）

排程器不再「派發即結案」，而是把每次派發綁上唯一 run_id，由 Chat._worker 跑完後透過 on_complete 回寫最終結果；即使 worker 在 1 毫秒內極快結束，也不會被派發段的鎖覆寫狀態：

圖 B1-1：派發與結算分離。透過 settled_run_id == run_id 檢查，無論是慢 worker 或 1ms 秒敗 worker，都不會互相覆寫 next_run 與 last_status。

核心想法二：排程完整狀態機與熔斷策略

圖 B1-2：排程狀態轉換與熔斷機制。瞬斷給 4 次指數退避自癒機會，連續失敗 5 次自動停用避免空轉燒算力。

長程防漂移四道護欄

防壓縮震盪

動態視窗預壓縮（扣除 fixed_tokens）

dynamic_window = max(1, W - fixed_tokens) dynamic_tokens = max(0, context_tokens - fixed_tokens) if dynamic_tokens > floor(dynamic_window * 0.5): agent._try_compact(force=True)

在 worker 鎖內執行，消除鎖外競態；且系統提示、AGENTS.md、persona 與工具 schema 再大也不會單獨觸發震盪壓縮。

防狀態與時間漂移

重試去重 ＋ 跨日刷新 ＋ 固定需求釘選

  • 尾端重複提示去重：Agent.run() 若偵測 session.messages[-1] 已是完全相同的未回覆 user prompt，直接沿用不重複寫入，守住 append-only journal 不變量。
  • 跨日 Date 刷新：Agent._refresh_date() 每輪檢查日期，跨午夜自動更新 system prompt 的 Date: 標頭。
  • 固定需求釘選：排程觸發前自動 sync_requirements()，verbatim 需求跨壓縮與重啟零漂移。
