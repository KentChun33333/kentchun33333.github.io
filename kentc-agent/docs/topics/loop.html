02 · 任務如何真的往前走

一次 run 可以包含多個 operation

問題

任務需多次「模型 → 工具 → 模型」來回，任一回覆都可能截斷、無效或中斷；模型也可能查到呼叫次數用盡仍無答案。

核心想法

每次來回是可追查的 operation：先驗證再保存、無效則乾淨重試、中斷時補齊工具結果；每次請求附剩餘呼叫次數，促使提早收斂。

依據

加提醒前，記憶回復 4 次 trial 全用完 8 次呼叫、無答案；加入後 4 次皆有答案、3 次通過（見 ③）。

問題：每一步都可能出錯

  • 輸出不完整：串流中斷、超出輸出上限、工具參數非合法 JSON → 照收則下一輪帶半截內容或不可執行的呼叫。
  • 協定被打斷：取消或例外 → 已送出的工具呼叫缺結果 → 下次請求對話不合法。
  • 不會收尾：不知剩餘次數＋提示要求「多查證」→ 有答案仍搜尋，撞上限，成果全數作廢。
  • 不可信的工具結果：文件或命令輸出可含「忽略之前的指示」類文字。

核心想法：可驗證、可修復、知道剩多少

Agent.run(prompt) 處理一個輸入；每輪一個 operation（模型請求＋回覆與工具批次）。請求可內部重試 → operation ≠ 一次 HTTP 請求。

更新部署能力 → 加入使用者訊息 → [ 準備上下文 → 呼叫模型 → 驗證完整性與輸出契約 → 保存回覆 → 工具執行／結果整理 ] └─ 無工具呼叫：回傳答案 └─ 有工具呼叫：保存工具結果 → 下一個 operation

逐步看一次代理迴圈

可點選 · 非實際執行

四個核心工具的責任

read：讀檔、分頁、解析文件。
write：建立／覆寫。
edit：精確比對替換。
bash：命令、搜尋、列檔、精確計算。
CLI 另加經篩選的 web_search（見 00 · 三種使用層）。

Studio 無 bash：總額取自 SQL 擷取關鍵值，其餘數字列算式供分析師核對（詳見 10 · Studio 應用）。

正常停止與異常停止要分清楚

串流先顯示，驗證通過才保存。截斷／無效 → 丟棄，有限次乾淨重試；重試耗盡、超過 max_turns、拒絕回覆 → 明確停止。取消或錯誤 → 盡量補齊已保存工具呼叫的結果。

未通過的回覆不當證據、其工具呼叫不執行；格式正確 ≠ 事實正確。

剩餘呼叫次數提醒

有次數上限且有工具的代理，每次請求尾端附暫時提示，如：Model-call budget: call 3 of 8; 5 left after this one. Plan to finish within them: once the requested facts are supported by evidence, answer instead of searching further. 最後一次改為「立即以已收集證據回答」。只隨該次請求送出、不寫入 session → 不累積、不進摘要；置於末端 → 前綴不變，本機前綴快取仍有效。無工具單次代理（如篩選子代理）不附。

程式：Agent._budget_notice（v1、v2 相同）。

取消不是交易回滾。 已寫檔、已執行命令不撤銷；修復只保工具訊息配對與工作階段可續。磁碟不可寫時不保證持久化。
工具結果進上下文前皆經安全檢查。 context/safety.py 純規則（不呼叫模型，中英文）標記：覆寫指示、角色切換、「不要告訴使用者」、外傳資料或讀密鑰、curl | sh 等；移除零寬、雙向覆寫、Unicode 標籤等隱藏字元。標記結果保留資料、前置不可信警告，追蹤記 safety。警報線，非邊界；控制靠工具權限。

依據：提醒前後實測
