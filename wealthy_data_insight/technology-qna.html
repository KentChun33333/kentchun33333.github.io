01 · Cache mechanics in an LLM server

Reuse computation before generating the next token.

Most serving stacks accelerate repeated prefixes by reusing previously-computed key/value attention states. The exact cache policy is implementation-specific, but the mechanics are broadly the same.

SHORT ANSWERCache saves repeated prefill, not reasoning itself.

A cache hit means the server can reuse attention states for an identical prefix. It does not mean the model remembers the answer; it means the same prefix does not need to be recomputed.

Implementation detail: vLLM, SGLang, TensorRT-LLM, llama.cpp and others differ in paging, hashing, eviction and scheduler behavior. This slide intentionally shows the shared conceptual model.
02 · Offline knowledge graph update

Do not “overwrite the graph.” Reconcile evidence into a new version.

An offline graph refresh should separate raw observations from canonical entities, deduplicate candidate matches, explicitly resolve conflicts, and retain provenance so the resulting graph is auditable.

SHORT ANSWERDeduplicate entities; version facts.

Entity resolution decides whether two records refer to the same thing. Conflict resolution decides which claims are currently trusted. These are separate problems and should remain separately auditable.

A practical production pattern is “raw observation → canonical entity → versioned claims,” with effective dates and source lineage retained for every important relationship.
03 · Simple retrieval-driven agent loop

Plan, retrieve, reason, evaluate — and only loop when evidence is insufficient.

A reliable agent loop keeps the deterministic control flow outside the LLM where possible. The model proposes actions, retrieval supplies evidence, and an evaluator decides whether another loop is actually necessary.

What to explain

AGENT CONTROL
1
Frame the taskTranslate the user request into explicit information needs and exit criteria.
2
Retrieve evidenceUse tools to fetch relevant facts instead of asking the model to “remember.”
3
Synthesize with citationsReason over the retrieved context, not over an unbounded hidden state.
4
Evaluate against exit rulesEnough evidence? Conflicts resolved? Required fields complete?
5
Loop or answerLoop only when a specific evidence gap remains; otherwise exit.
SHORT ANSWERThe loop should be controlled by explicit state and exit conditions.

The LLM can decide what to investigate next, but the workflow should know why it is looping, how many times it may loop, and what conditions allow it to stop.

This is intentionally a minimal architecture: one planner/router, one retrieval layer, one reasoning step, one evaluator. More agents do not automatically make the system better.
